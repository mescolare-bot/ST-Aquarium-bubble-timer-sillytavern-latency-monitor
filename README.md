# 鱼缸后端监控 · SillyTavern Latency Monitor

给 SillyTavern 做的生成链路监控面板。每次生成花在哪一段、上游到底收了多少 token、
哪些请求出了异常、大概花了多少钱——这些都记下来并在面板里展示。

## 能看到什么

- **分段耗时**：前置处理、上游响应头、首 token、流式输出各占多久，卡在哪一段一眼能看出来
- **prompt 体积拆解**：按 role 统计条数和字符数，定位是系统提示太大、历史太长、还是某条超长消息拖慢了生成
- **异常诊断**：识别可处置的异常类型并给出优化建议
- **成本估算**：按模型配置的价格换算，支持缓存命中和峰谷计价
- **历史与聚合**：按用途筛选、按聊天归组、7/14/30 天日聚合
- **等待队列**：查看和管理等待中的请求

## 安装

有两种装法，先选一种：

| | 精简版 | 完整版 |
| --- | --- | --- |
| 怎么装 | 在酒馆界面里贴仓库地址 | 在跑酒馆的机器上执行脚本 |
| 要不要碰服务器 | 不用 | 要 |
| 会不会改酒馆本体 | 不会 | 会（打补丁，酒馆升级后要重打） |
| 记录存在哪 | 你当前这个浏览器里 | 服务器上 |
| 换浏览器或设备看 | 看不到 | 看得到 |
| 分段耗时 | 只有一个总耗时 | 前置处理 / 上游响应头 / 首 token / 流式输出 分开 |
| token 用量 | 多数情况有 | 全都有 |
| 其余功能 | 都有 | 都有 |

**拿不准就先装精简版。** 它不改你服务器上的任何东西，用下来觉得需要分段耗时再升级，
之前记的东西不会丢。

### 精简版（三步）

1. 酒馆界面 → 扩展（插头图标）→ `Install extension`
2. 粘贴 `https://github.com/mescolare-bot/ST-Aquarium-bubble-timer-sillytavern-latency-monitor.git`，确认
3. 按 `Ctrl + Shift + R` 强制刷新

装完右下角会多一个悬浮图标，点开就是面板。悬浮图标的颜色由你自己在设置里选，两种装法都一样；
想确认当前跑在哪一种，看面板标题右边那个小圆点：绿色是精简版，蓝色是完整版，红色是连不上后端。
鼠标停在圆点上会写明当前是哪一种。

精简版的三个限制先说在前面：

- **记录只存在当前这个浏览器里。** 换浏览器、换设备、清掉浏览器数据都会看不到。
- **分段耗时只有一个总数。** 浏览器只知道"我发出去"和"我收到"，中间酒馆花了多久、上游花了
  多久，它分不开。想回答"到底是酒馆慢还是上游慢"就得装完整版。
- **流式生成的 token 用量不保证拿得到。** 精简版只能靠给自定义接口注入
  `stream_options.include_usage` 去要用量，所以有三种情况会落空：接入源选 `OpenAI` 时酒馆
  压根没给前端留口子；你自己填了"附加参数"时插件会主动避让，以免弄坏你的配置；接口收下了
  这个字段却不回用量——各类中转的"假流式"经常如此。三种情况面板都会在「usage 信号」那一行
  写明是哪一种，而不是显示 0 或干放一个"-"让你猜。装完整版则不受这些限制。

### 完整版

必须在跑酒馆的那台机器上执行，因为浏览器写不了 `src/`、`plugins/` 和 `config.yaml`。

```bash
git clone https://github.com/mescolare-bot/ST-Aquarium-bubble-timer-sillytavern-latency-monitor.git
cd ST-Aquarium-bubble-timer-sillytavern-latency-monitor
node install.mjs <酒馆根目录>
```

然后重启酒馆，浏览器按 `Ctrl + Shift + R` 强制刷新。脚本是幂等的，升级酒馆之后重跑一次即可；
`--dry-run` 只报告不落盘，`--uninstall` 可以完整还原。

**完全没碰过命令行？** 看 [`docs/installation-beginner.md`](docs/installation-beginner.md)，
从"怎么打开命令行"开始，每一步都写了该看到什么、不对时怎么办。

需要手动安装，或者脚本报"找不到锚点代码"时，看 [`docs/installation.md`](docs/installation.md)。
补丁没装全时面板会直接在记录列表上方报出来，包括缺了哪几处、各自会导致什么后果。

### 从精简版升级到完整版

按上面完整版的步骤跑 `install.mjs` 就行。脚本会自动删掉贴 git 装的那一份——两份同时存在的话
酒馆会把扩展加载两遍，出来两个面板。

**之前记的东西不会丢，但也不会自动并进新统计。** 升级后设置页顶部会出现"浏览器里还留着 N 条
旧记录"，可以单独查看、导出成 JSON、或者清除。不自动合并是因为两边的耗时口径不一样：精简版
记的总耗时含酒馆自身的处理时间，混进同一份平均值里，出来的数字谁也不代表。

## 仓库结构

```
index.js / style.css / manifest.json   前端扩展（两种装法都要）
lite/                                  精简版专用：浏览器端采集、IndexedDB 存储、本地接口
backend-monitor-minimal/
  latency-monitor.js                   后端采集与落盘（装进酒馆 src/）
  server-plugin/index.js               查询接口与记录维护（装进酒馆 plugins/）
  settings-ui/  shared/                两处共享模块，完整版下各需放两遍
docs/
  installation-beginner.md             零基础安装指南
  installation.md                      完整版安装与手动步骤
  engineering-notes.md                 改代码之前必读
```

`shared/` 里的分析逻辑是浏览器安全的，精简版和完整版共用同一份，保证两边算出来的
异常类型和优化建议一致。`scripts/` 下有两个守卫脚本负责在改动后检查这一点。

## 改代码之前先读

[`docs/engineering-notes.md`](docs/engineering-notes.md) 记录了几条量化过的工程约束，
以及若干"看起来是 bug、其实是数据缺失"的结论：

- 接口载荷体积约束——为什么 `limit` 必须有上限、为什么列表不下发 `prompt_breakdown`
- 只有前端知道的字段该怎么随请求体下发，以及三个必踩的坑（含"`0` 是合法楼层"）
- 后端只在请求结束后才落盘，由此**否定掉的一整类实现思路**
- 聊天维度历史数据的起始日期限制
- 远程部署与更新时反复踩到的问题

## 已知限制

仅精简版：

- **记录只存在装它的那个浏览器里**，换设备看不到，清浏览器数据会丢。
- **分段耗时塌缩成一段**，无法区分酒馆预处理和上游响应各占多久。
- **`OpenAI` 源 + 流式输出拿不到 token 用量。** 自定义源是靠往 `custom_include_body`
  注入 `stream_options.include_usage` 拿到的，`OpenAI` 源没有对应的透传口。
- **少数中转不认注入的字段。** 遇到时会自动去掉注入重试一次并记住这个接口，
  代价是它之后都没有流式 token 数，但不会影响你正常生成。

两种装法共同的限制：

- **明细只保留最近一批，历史统计不受影响。** 完整版留最近 3000 条、精简版留最近 5000 条，
  超出的会被压成只含统计字段的存根（约 288 字节，是完整记录的 4.5%）继续留着。
  这意味着**日聚合、异常率、token 与花费统计是永久的**，但超过保留条数的那些生成，
  点不开排障详情了。设上限是必须的：记录会被整份读进内存再逐行解析，实测 6628 条
  就要 375 毫秒，面板每刷新一次付一遍，不封顶迟早会卡。
- **「清空全部记录」会连存档一起清**，趋势图和日聚合也跟着归零。按勾选删除、
  只删正常记录这两种不动存档——存根为了省体积没留 id，对应不到具体是哪几条。
- **完整版极小概率会漏掉一条记录。** 明细超额时要把文件整份重写一遍，而落盘的那半边
  是酒馆进程里另一个模块实例，共用不到重写这侧的队列。重写已经把窗口压到最后一次
  文件替换的几毫秒内，并且会把这期间新追加的内容补回去，但正好卡在替换那一瞬的
  那条会丢。按每分钟一次生成、每 200 条触发一次重写估算，大约每 80 万次生成遇上一次，
  丢的也只是一条记录，不会损坏文件或影响其他记录。
- **要求 SillyTavern 1.18.0 或更新。** 逐版本核对过补丁锚点：1.18.0 九处全部命中；
  1.15–1.17 缺流式那一处，装上会少掉流式阶段的日志；1.14 及更早基本全部对不上。
  `manifest.json` 里的 `minimum_client_version` 已按实测值写成 `1.18.0`，
  版本不够时酒馆不会加载这个扩展，而不是让你装上以后再慢慢发现少东西。
- **只支持单用户实例。** 数据路径里的 `default-user` 是写死的，多用户时记录会混在一起。
- **接口的访问控制完全跟随酒馆本体。** 插件路由注册在酒馆那套中间件之后，`basicAuth`、
  白名单、CSRF、登录校验一视同仁地管着它，不需要也没有额外的鉴权开关。但反过来说：
  如果你在 `config.yaml` 里写了 `securityOverride: true` 又开了 `listen`，那么裸奔的
  不只是这个面板，你的聊天记录和角色卡一样在外面。**别开它**——正常情况下酒馆会在
  没有白名单也没有 basicAuth 时直接拒绝启动，那是它在保护你。
- **本体补丁会被酒馆升级覆盖**，每次更新后要重新打。
- **流式 usage 偶发归零**（约 3.7%），成因尚未完全查清，详见工程笔记第六节。
